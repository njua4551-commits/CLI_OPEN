# Decisiones técnicas

- **D01 · Motor y alcance.** OpenCode aporta CLI, TUI, sesión y extensiones existentes. Codex desarrolla el proyecto. El clon original queda en su ruta actual. Las pruebas usarán una copia separada y el núcleo queda fuera del alcance de cambios.
- **D02 · Base P-1.** `v2.3.2` en `c0ad18b402eb2827fc1ee71c171b1177b3fc02d1`. La selección fija la revisión a calificar. La decisión de avanzar depende de los resultados. [Release oficial](https://github.com/anomalyco/opencode/releases/tag/v2.3.2)
- **D03 · Continuidad.** Git propio en la carpeta contenedora, excluyendo `upstream/` y el área temporal `.fase1/`. `ESTADO.md` sirve como punto de entrada. Los registros bajo `docs/` conservan justificación, cambios y evidencia por hito. Si aparece evidencia que afecta una decisión aprobada, documentar la discrepancia y solicitar revisión antes de cambiarla.
- **D04 · Baseline.** Reutilizar el build y la prueba de ciclo de vida de CI. Evitar `dev:live` en la sesión privada porque se conecta al servicio existente. Verificar los flags con el binario exacto antes de usarlos.
- **D05 · Repositorio público.** El usuario designó `https://github.com/njua4551-commits/CLI_OPEN.git` como `origin`. Verificar referencias y contenido antes de publicar. Conservar cualquier historial remoto; usar push normal.
- **D06 · Autonomía.** El usuario autorizó acciones rutinarias y commits locales dentro de la fase vigente. Las nuevas publicaciones requieren autorización. Véase [AGENTS.md](../AGENTS.md).
- **D07 · Inferencia de P-1.** Sustituir la calificación física local por pruebas deterministas contra una API simulada en loopback y una prueba real separada con `openai/gpt-oss-20b:free` en OpenRouter. Presupuesto USD 0, fixtures sintéticos, sin fallback y secreto inyectado como `OPENROUTER_API_KEY`. Conservar la validación física local como pendiente y tratar Kaggle como destino remoto explícito. [Modelo y precio](https://openrouter.ai/openai/gpt-oss-20b%3Afree/pricing)
- **D08 · Prueba integral.** Usar la CLI compilada y su proveedor compatible con OpenAI. El fixture simula únicamente el proveedor y el servicio señuelo. OpenCode ejecuta sus herramientas reales sobre archivos sintéticos con configuración privada.
- **D09 · Puerta de Fase 2.** El usuario autorizó iniciarla automáticamente cuando P-1 cumpla sus criterios de aceptación. La autorización termina antes de Fase 3.
- **D10 · Propuesta de sustitución.** `liquid/lfm-3-1.7b:free` tiene un endpoint con soporte de herramientas y precios cero de entrada y salida. La sustitución del modelo fijado en D07 requiere aprobación. [Catálogo de endpoints](https://openrouter.ai/api/v1/models/liquid/lfm-3-1.7b:free/endpoints)
- **D11 · Sustitución confirmada.** Se fijó `liquid/lfm-3-1.7b:free` tras la aprobación y el preflight de precio y herramientas. Si deja de estar disponible, seleccionar y registrar el candidato gratuito más competente con endpoint activo y herramientas, usando solo datos sintéticos y sin fallbacks de pago.
- **D12 · Supervisor P0.** Python de biblioteca estándar para el punto de entrada mínimo. El perfil PLAN se limita a dos operaciones locales declaradas. Las políticas se expresan en el supervisor; la entrada del usuario no las modifica. OpenCode se conserva como motor fijado para la integración posterior.
- **D13 · Broker DIAG.** Reusar MCP stdio y la negociación legacy del cliente fijado. El catálogo usa interfaces Linux con biblioteca estándar, sin comandos externos ni parámetros de rutas. Se prioriza Linux x86_64 y se conservan los contratos para añadir futuros backends de Windows y macOS.
- **D14 · Integración MCP.** Calificar el descubrimiento con una sesión real de la CLI contra un proveedor simulado. Aceptar el objeto de metadatos del transporte y descartarlo. Los argumentos siguen limitados a un objeto vacío.
- **D15 · Inicio de aislamiento Linux.** Probar Bubblewrap con namespaces obligatorios y montajes explícitos en datos sintéticos antes de conectar la frontera al runtime de producto. El resultado parcial no habilita escrituras de producto.
- **D16 · Politica de la sesión DIAG.** Usar configuración de confianza y desactivar la configuración de proyecto en la sesión calificada. La herramienta integrada `skill` puede aparecer en el catálogo aun cuando la invocación esté denegada. Verificar permisos también en el resultado de invocación.
- **D17 · Lanzador de calificación.** El supervisor ejecuta un fixture fijo con Bubblewrap y falla cerrado si el backend es inexistente, rechaza los namespaces o agota el tiempo. El doctor sigue consultando el estado efectivo. La Fase 5 comenzó con una copia sintética separada del código original.
- **D18 · Revisión transaccional.** El supervisor prepara cambios explícitos en una copia desechable. La validación y edición se ejecutan dentro de Bubblewrap. Un diff caduco se rechaza y el supervisor carece de una ruta de aplicación al original. OpenCode permanece fijado para integrar sus herramientas de edición en esa frontera.
- **D19 · Edición nativa y publicación Git.** OpenCode ejecuta la herramienta `write` en la copia. El supervisor valida bytes y alcance, vincula la aprobación a la base y publica un commit en una referencia separada mediante una transacción. El índice y árbol de trabajo activos quedan fuera de la operación.
- **D20 · Inicio del gateway.** La inferencia de producto comienza sin rutas remotas habilitadas. El permiso de gasto y destino se diseñará aparte del permiso de edición.
- **D21 · Primer adaptador P3.** El gateway local realiza una solicitud no streaming a la IP fija de loopback y a un modelo explícito. Usa HTTP directo, sin proxies, redirecciones, credenciales ni reintentos. El transporte todavía no está integrado a la CLI. Un endpoint en loopback por sí solo no acredita inferencia física local.
- **D06 · Transporte del gateway.** Un solo validador y un destino fijo para stdin y `--listen`. El modo de escucha acepta el cuerpo que emite el proveedor OpenAI-compatible de OpenCode (`max_completion_tokens`, `stream_options`, roles `tool`) y acota los tokens a 512 en lugar de rechazar la solicitud. No reenvía `Authorization`, no sigue redirecciones ni reintenta. El cuerpo máximo sube a 128 KiB porque el prompt y el catálogo reales superan 16 KiB; respuesta y plazo no cambian.
- **D07 · Cierre de Fase 6.** La aceptación se acredita con el perfil local sintético. El presupuesto remoto, la aprobación por contenido y la calificación de un modelo físico local quedan aplazados y requieren autorización nueva. No hay ruta remota de producto habilitada.
- **D08 · Memoria de Fase 7.** Almacén JSONL por proyecto en `$XDG_STATE_HOME/cli-open/memoria`, fuera del repositorio y de la copia de OpenCode. La identidad del proyecto es el hash de su ruta real. La invalidación compara el SHA-256 de cada archivo referenciado al leer; una entrada obsoleta no se recupera. La memoria es contexto, nunca autoridad de permisos. No se duplica el almacenamiento de sesiones de OpenCode.
- **D22 · Adopción del Roadmap Estratégico Consolidado y Matriz de Reutilización.** Consolidación definitiva de la Fase 7 en subfases ordenadas F7.1 a F7.8, conservación de F0–F6, aplazamiento controlado de D07 y delimitación de F8 (distribución Linux x86_64 calificado) y F9 (futuras opciones remotas y restauración avanzada fuera de MVP). Se adopta el principio obligatorio "REUTILIZAR ANTES DE EXTENDER. EXTENDER ANTES DE REEMPLAZAR" con clasificación previa en 7 estados para evitar duplicar el runtime, gestor de sesiones, TUI, compactador, permisos o infraestructura multiagente de OpenCode V2.
- **D23 · Integración de Contexto en Loopback con Autoridad Nula.** El supervisor incorpora el sobre de memoria persistente como datos no confiables mediante delimitadores explícitos (`[UNTRUSTED_PROJECT_MEMORY_CONTEXT authority=none]`) y validación estricta de estructura y ausencia de credenciales en `implementacion/supervisor/context.py`. La sesión sintética de OpenCode en loopback (`tests/fase1-loopback.ts` y `tests/fase7-contexto-loopback.ts`) verifica que las instrucciones adversarias dentro del contexto no amplían permisos, no permiten escrituras fuera del área de trabajo, no alteran políticas del supervisor y no realizan llamadas de red fuera de loopback (servidor señuelo con 0 solicitudes).
- **D24 · F7.1 Línea base y auditoría de capacidades nativas.** Se establece la matriz de clasificación de propuestas F7 frente a OpenCode V2 (`docs/MATRIZ_F7.md`) y la suite de referencia `tests/fase7-lineabase.py`. Repo Map se clasifica `APLAZADA` hasta reutilizar Tree-sitter/LSP/ripgrep del motor fijado; no se crea un indexador independiente.

El candidato es un procesador opcional y determinista después de una recuperación autorizada. El hook `tool.execute.after` del SDK Effect puede modificar el resultado completado antes de normalizarlo. Antes de adoptarlo, verificar con un plugin aprobado que se conservan salida completa, vista previa y procedencia, y que los resultados de Code Mode no eluden el presupuesto. Reutilizar `Token.estimate`, el límite de contexto del modelo y el almacenamiento administrado. Limpiar solo bloques repetitivos identificados con reglas verificables. Si falta espacio, seleccionar secciones completas por consulta, mantener URL y ancla, marcar que la salida es parcial y permitir recuperar secciones adicionales. Sin caché nueva en el primer candidato. Si se justifica después, aislar por URL canónica, opciones y ámbito de permisos, con expiración, invalidación y tamaño máximo.

La recuperación externa permanece aplazada. Antes de habilitarla, calificar origen y destino efectivo, DNS y redirecciones, bloqueo de redes privadas e internas, límites de bytes, páginas y tiempo, y ausencia de efectos de instrucciones externas sobre permisos o herramientas. Conservar Bubblewrap y el perfil sin salida general. Mantener el texto como resultado de herramienta con procedencia y autoridad nula. Probar secretos, parsers, archivos comprimidos y contenido adversario con fixtures. El caso HTML adversario de la línea base solo comprueba que el texto visible se preserva y que el contenido de script se excluye.
